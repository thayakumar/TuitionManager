# Native one-time ASK readiness diagnostic

The supplied ask_diagnostic_v3.html is integrated as a native assessment, not an iframe. Its 3 background questions, 32 scored questions, bilingual prompts, flowchart, four skill areas, tier breakdown, prerequisites and action-plan rules are preserved. Duplicate student-name/class/school fields and reset/retake behavior were removed. Account identity supplies the student name and grade.

User-confirmed policy: a diagnostic is prepared on account creation; the tutor opens it when ready for the first regular class after the trial, then locks the results. The lifecycle is awaiting → open → in_progress → submitted → locked. Students can resume and review their single in-progress attempt. Submitting makes answers read-only. Tutor locking publishes a frozen result; a partial lock includes only saved work and treats unanswered skills as skipped. Admins can see drafts, all responses and reports; students receive results after locking. Parents have no new access.

Diagnostics has a searchable/paginated admin overview, student profile and dashboard links, student navigation, and regular-class/meeting shortcuts. Reports include overall/strand/difficulty results, background, skill gaps, timing hints and teaching actions. Timing remains browser-reported and is presented as a teaching hint, not a validated personality assessment.

Security: the GitHub repository is public, so the real uploaded question bank and answer key are not committed. They are imported once through the authenticated admin template endpoint into the private database. Public question DTOs remove keys and recommendations during the attempt. Frozen private snapshots preserve version integrity. Synthetic banks are used for committed tests. Original answer-key/report screenshots remain outside the public repository.

Verification: 102 automated tests and the production build passed. Six new real-SQLite scenarios cover account initialization without configured templates, private immutable template setup, one-attempt lifecycle, strict grading, frozen reports, request replay after newer saves, concurrent revisions, lock behavior, role/account isolation, forged grades and deactivation. Existing 96 tests remain green.

Seven browser scenarios pass with the actual original 35-question template in an isolated database: tutor gating and no key exposure; save/refresh/resume; other-student/unauthenticated/configuration isolation; complete original-question submission including the flowchart, text and numeric inputs; tutor review of all 35 rows and 100% test result; lock and automatic student read-only results; partial locking and 390px layout; searchable tutor overview. These are grouped into seven recorded scenarios in browser-results.json. No production students were tested or marked, and no fake assessments were created in production.

A setup step imports the user's genuine assessment into production configuration after deployment. It does not open or start any student's assessment. Numeric scoring intentionally rejects malformed partial numbers such as a correct prefix followed by letters, which the standalone parseFloat implementation could accept.
